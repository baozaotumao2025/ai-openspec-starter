# Specs 阶段规则

## 阶段目标

Specs 描述系统可观察、可验证的行为要求。

只描述系统应该做什么，不描述具体代码结构或实现方式。

## 领域术语

- 如果存在 `docs/glossary.md`，所有领域实体、角色、权限、状态和业务动作必须与其定义一致。
- 不得使用模糊或通用词汇替代已有领域定义。
- 同一概念在所有 Spec 中必须保持统一命名。

## EARS 需求表达

可验证的行为要求优先使用 EARS 形式：

`The system shall [行为] when/if/while [条件]`

每项重要行为应根据实际业务情况考虑：

- 正常路径；
- 前置条件；
- 空值和边界条件；
- 异常与拒绝路径；
- 幂等要求；
- 并发要求。

不得为了形式完整而编造当前业务不存在的场景。

## 状态跃迁

涉及实体状态变化时，必须明确：

- 当前允许的前置状态；
- 触发动作；
- 目标状态；
- 非法状态下的拒绝行为。

优先采用：

`The system shall transition [entity] to [target state] when [trigger] while [valid precondition].`

以及：

`The system shall reject the transition when [invalid state condition].`

## 技术无关性

Spec 描述业务行为和系统契约。

- 不写具体类名、数据库表名或内部函数调用。
- 跨模块行为描述为可观察契约、领域事件或抽象能力。
- 具体技术实现放到 `design.md`。

## 可验证性

每条重要 Requirement 都应能够映射到后续测试或其他确定性验证方式。

无法验证的模糊描述应在进入实现前澄清。

## 权限相关行为

如果当前 Change 涉及以下任一方面：

- 身份认证或主体传递；
- 授权或访问控制；
- 角色、权限、成员关系、所有权或共享关系；
- 对受保护资源的访问或操作；
- 跨用户、组织、租户、项目、工作区或其他资源边界的访问；
- API Key、服务主体、自动化任务或代理执行；
- 任何涉及“谁可以在什么条件下对什么资源执行什么操作”的行为；

则必须读取并遵循：

`docs/rules/authorization.md`

权限要求应作为可观察、可验证的系统行为写入 Specs。

重要权限 Requirement 应尽可能明确：

- 哪类 principal 发起操作；
- 执行什么 action；
- 目标 resource 是什么；
- 在什么 context 下允许；
- 在什么条件下必须拒绝；
- 拒绝时系统表现为何。

不得只写“需要鉴权”“需要 RBAC”“检查权限”或其他无法确定允许与拒绝行为的描述。

具体授权实现位置、调用链和技术方案属于 Design，不写入 Specs。
