# 测试策略

## 适用范围

本规则用于 Apply 阶段的代码实现与验证。

测试的目标不是追求覆盖率数字，而是证明 Specs 中的重要行为和不变量真实成立。

## 测试优先

新增或修改业务行为时，默认遵循：

**RED → GREEN → REFACTOR → VERIFY**

### RED

先创建能够表达预期行为的失败测试。

测试必须因为目标行为尚未实现而失败，而不是因为测试本身错误、环境错误或无关依赖失败。

### GREEN

只实现让当前测试通过所需要的最小业务代码。

不得在 GREEN 阶段顺便加入额外能力或无关重构。

### REFACTOR

测试通过后再进行必要的局部重构。

重构不得改变已经确认的外部行为。

### VERIFY

执行当前 Task 定义的验证信号，并确认不存在相关回归。

## Specs 与测试映射

重要 Spec Requirement 应至少存在一种确定性验证方式。

测试应覆盖实际存在的：

- 正常路径；
- 前置条件；
- 边界条件；
- 异常或拒绝路径；
- 状态跃迁；
- 幂等要求；
- 并发要求。

不得为了填满测试矩阵而编造不存在的业务场景。

## 四维测试视角

针对重要业务行为，应评估以下四个维度：

1. **Happy Path**：正常输入与正常状态；
2. **Boundary**：空值、极值、临界状态；
3. **Invalid / Failure**：非法输入、非法状态和依赖失败；
4. **Invariant / Interaction**：状态不变量、幂等、并发和关键交互。

不是每个 Requirement 都必须机械拥有四个测试；应根据真实风险选择。

## 确定性测试

时间、随机数、UUID 等不确定性依赖应尽量通过显式依赖隔离，例如：

- Clock / Time Provider；
- Random Provider；
- ID Generator。

核心业务测试不得依赖真实当前时间或不可控随机结果。

## 单元测试

核心业务规则优先使用：

- 内存 Fake；
- Mock；
- Stub；
- 纯函数测试。

单元测试默认不访问：

- 网络；
- 外部服务；
- 真实文件系统；
- 真实生产数据库。

适合使用轻量本地数据库验证持久化契约时，应明确其测试层级，不伪装成纯单元测试。

## Adapter 与契约测试

外部依赖 Adapter 应验证：

- 输入输出映射；
- 错误转换；
- 超时与失败契约；
- 与 Port 定义是否一致。

当 Fake / Mock 作为 Port 的替代实现时，应通过契约测试避免测试替身与真实 Adapter 行为漂移。

## 测试层级

优先保持测试金字塔：

1. 快速、确定性的单元测试；
2. 必要的组件 / Repository / Contract 测试；
3. 少量关键集成测试；
4. 少量关键端到端测试。

不要用大量 E2E 测试替代可在领域层完成的确定性验证。

## 执行速度预算

默认目标：

- 单元测试集合：30 秒以内；
- 集成测试集合：3 分钟以内；
- 端到端测试集合：15 分钟以内。

这些是反馈速度目标，不是为了数字本身删除必要测试。

超过预算时应检查测试层级、外部依赖和重复场景。

## 三次失败原则

同一测试或实现问题连续三次尝试仍不能通过时：

1. 停止猜测式修改；
2. 保存关键错误信息；
3. 总结已经尝试的方法；
4. 重新检查 Specs、Design、上下文和假设；
5. 必要时标记为阻塞项。

不得：

- 删除失败测试；
- 放宽正确断言；
- 使用 skip / xfail 隐藏问题；
- 通过硬编码测试数据制造假通过。

## Mutation Testing

Mutation Testing 只用于高价值、纯逻辑、风险较高的代码，例如：

- 核心业务规则；
- 权限判断；
- 金额或期限计算；
- 状态机；
- 高风险核心业务中的关键确定性规则。

不要求对整个代码库执行 Mutation Testing。

如果对目标范围执行 Mutation Testing，存活 Mutation 应被分析并补充有效测试，或明确记录合理原因。

## 完成条件

一个业务 Task 的测试完成至少意味着：

1. 对应 Requirement 有确定性验证；
2. 新增测试先证明过 RED；
3. 当前实现通过目标测试；
4. 必要的相关回归测试通过；
5. 测试没有依赖不可控环境；
6. 没有通过跳过或削弱测试隐藏失败。

### Mutation Testing 通过标准

Mutation Testing 不是所有代码的默认门禁，而是风险驱动的专项验证。

一旦某个目标被纳入 Mutation Testing 范围：

- 不得仅报告 mutation score 后结束；
- 每个 Survived Mutant 都必须被分析；
- 能通过有效测试杀死的 Mutation 必须补充测试；
- 等价 Mutation 或工具误报可以保留，但必须明确记录原因；
- 存在无法解释的 Survived Mutant 时，该目标不得视为验证通过。

对于高风险核心业务规则、权限判断、金额与期限计算、状态机等确定性逻辑，若 Verify 已决定执行 Mutation Testing，则默认目标是：

`unexplained survived mutants = 0`

## 测试可靠性盲区

### Mock 过度信任

Mock / Fake 只能验证当前代码是否遵循已定义契约，不能证明真实外部依赖一定如此工作。

对于重要 Adapter 或跨系统集成：

- 应验证真实契约、序列化格式和错误映射；
- 必要时使用 Contract Test 或集成测试；
- 应覆盖超时、失败响应和协议异常；
- 不得仅因为 Mock 测试全绿就宣布外部集成正确。

### 测试间隔离

测试不得依赖其他测试先执行。

禁止通过测试间共享可变状态形成隐式顺序依赖。

每个测试应能够独立建立自己的前置状态，并在必要时清理自身副作用。

### 顺序敏感性检查

当测试套件和当前工具链支持时，应评估使用随机顺序或其他方式检查测试间隐藏依赖。

不得为了满足本规则而自行安装测试插件或修改工具链。

如果发现测试只能按特定顺序通过，应视为测试隔离缺陷，而不是固定执行顺序来掩盖问题。

## Port 测试替身策略

Port 是否需要专门的 Fake / InMemory Adapter，应根据测试需求决定，而不是机械要求每个 Port 都创建一个测试实现。

当 Port 代表以下依赖时，应优先提供确定性的测试替身：

- 外部网络服务；
- 数据存储；
- 时间；
- 随机数；
- ID 生成器；
- 消息系统；
- 其他会使单元测试产生外部 I/O 或不确定性的能力。

测试替身可以采用：

- Fake；
- InMemory Adapter；
- Stub；
- 简单 Mock。

优先选择能够清晰表达行为且维护成本最低的方式。

不得为了满足形式要求，为简单 Port 创建无实际测试价值的复杂 Mock 类。

如果同一个测试替身被多个测试长期复用，或其行为本身构成重要契约，应考虑提供稳定的 Fake / InMemory Adapter。

对于重要 Port，Fake / Mock 与真实 Adapter 之间应通过契约测试或等价验证降低行为漂移风险。

## 权限行为测试

如果当前 Task 涉及以下任一方面：

- 身份认证或主体传递；
- 授权或访问控制；
- 角色、权限、成员关系、所有权或共享关系；
- 对受保护资源的访问或操作；
- 跨用户、组织、租户、项目、工作区或其他资源边界的访问；
- API Key、服务主体、自动化任务或代理执行；

则必须读取并遵循：

`docs/rules/authorization.md`

权限测试不能只验证允许路径。

应根据当前 Requirement 和实际风险覆盖相关的正向与反向场景，例如：

- 合法 principal 在满足条件时被允许；
- 未认证主体被拒绝；
- 权限不足主体被拒绝；
- 无权访问其他主体资源；
- 跨组织、租户、项目、工作区或其他隔离边界的访问被拒绝；
- 所有权、成员关系、共享关系或资源状态变化后的行为；
- 不同入口是否保持一致的授权约束；
- 不同主体类型是否经过正确的授权路径；
- 身份和授权上下文在调用链中是否正确传播；
- 授权上下文丢失、替换或被扩大时是否能够被安全拒绝。

不得通过管理员、超级用户或高权限服务主体替代正常业务主体路径来证明权限实现正确。

测试应能够对应 Specs 中定义的：

- principal；
- action；
- resource；
- context；
- 允许条件；
- 拒绝条件。

如果授权行为依赖项目边界之外的组件，应读取并遵循：

`docs/rules/external-dependency.md`

Mock、Stub、Fake 或 InMemory Adapter 只能证明当前测试替身定义的行为。

当正确性取决于外部依赖的真实契约、配置或运行行为时，Mock / Fake 不能作为唯一证据。

应根据风险补充适合的确定性验证，例如：

- Contract Test；
- Integration Test；
- 对正式 API / Schema / Protocol 的验证；
- 必要的真实 Adapter 测试；
- 受控环境中的运行态验证。

具体采用哪种验证方式，应由当前 Change 的风险和外部依赖性质决定，不在本通用规则中预设固定测试技术。
