# Tasks 阶段规则

## 阶段目标

Tasks 将已经确认的 Specs 和 Design 转换成可执行、可验证、依赖关系明确的实施计划。

不得在 Tasks 阶段重新发明需求或改变已经确认的架构决策。

## 三波次任务拓扑

任务优先按依赖关系组织为三个 Wave。

### Wave 1：前置阻断项

用于必须先完成的基础契约或结构变化，例如：

- 数据库 Schema / Migration；
- Port / Protocol / Interface；
- DTO / 公共契约；
- 必要的 Mock / Fake；
- 其他会阻塞后续工作的基础能力。

### Wave 2：核心原子实现

用于实现具体业务行为。

要求：

- 每个任务聚焦一个明确目标；
- 核心修改范围尽量控制在 1～3 个文件；
- 优先实现可独立测试的小单元；
- 不把多个无关关注点塞进同一任务。

### Wave 3：汇合与集成

用于：

- 路由与装配；
- 跨模块联动；
- 领域事件订阅；
- 契约测试；
- 集成测试；
- 端到端闭环验证。

## 原子任务要求

每个任务必须包含：

1. 明确目标；
2. 明确依赖；
3. 明确完成条件；
4. 明确验证方式。

存在依赖时标记：

`[依赖: <task-id>]`

不存在依赖且可以安全并行时标记：

`[可并行]`

## 完成信号

每个原子任务必须包含确定性的验证方式。

验证方式应使用当前项目真实存在的命令、测试、静态检查、契约检查或可观察结果，例如：

`[验证: <当前项目实际存在的确定性验证命令或检查>]`

不能使用“看起来正常”“应该可以”等主观判断作为完成标准，也不得为了填写验证信号而虚构项目中不存在的命令。

## 任务粒度

- 不拆成纯机械操作的伪任务；
- 不创建跨大量文件、跨多个关注点的巨型任务；
- 如果单个任务预计需要修改大量模块，应重新评估 Design 是否需要进一步拆分。

## Specs / Design 可追溯性

每个任务都应该能够追溯到：

- 某条 Spec Requirement；或
- 某项 Design 决策。

无法追溯的任务不应进入实施计划。

## 人工 Gate

Tasks 完成后，在进入 Apply 前应向用户汇报：

1. Wave 结构；
2. 关键依赖关系；
3. 预计影响的主要文件或模块；
4. 尚未解决的风险或决策。

存在关键未决问题时，不得擅自进入 Apply。


## 权限相关任务

如果当前 Change 的 Specs 或 Design 包含权限行为，Tasks 必须把已经确认的授权要求落实为可执行、可验证的任务。

至少根据实际 Change 覆盖：

- 授权执行点的实现；
- 主体与授权上下文传递；
- 资源范围约束；
- 关键拒绝路径；
- 正向权限测试；
- 反向权限测试；
- 必要的外部依赖 Contract / 集成验证。

不得在 Tasks 阶段重新定义角色、资源边界或授权责任。

如果任务拆分过程中发现 Specs 或 Design 无法回答某个关键授权问题，应停止任务细化并返回对应 artifact 修正，而不是在 `tasks.md` 中临时决定。
