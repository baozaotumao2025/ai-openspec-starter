# 工程执行规则

## 适用范围

本规则用于 Apply 和 Verify 阶段执行代码检查、测试、构建和其他确定性工程验证。

## 基本原则

任何代码修改都应尽量通过可重复执行的命令进行验证。

不得仅凭：

- 阅读代码；
- 主观判断；
- “看起来正确”；
- Agent 自己的推理；

宣布任务完成。

## 命令事实来源

执行工程命令前，必须先确认项目当前真实可用的工具链。

优先从以下位置识别：

- `pyproject.toml`
- `package.json`
- `Makefile`
- `justfile`
- `Taskfile.yml`
- 项目脚本目录
- CI 配置
- 当前 Change 已确认的工程说明

不得凭旧项目规则或经验自行假设某个命令存在。

例如，在没有确认 Makefile target 前，不得直接假设：

`make typecheck`

一定可用。

## 验证命令分类

项目形成稳定工具链后，应尽量为以下能力提供确定性命令：

### Targeted Test

运行当前 Task 或 Feature 直接相关的测试。

优先于每次都执行全量测试。

### Type Check

执行项目实际使用的严格类型检查。

### Lint

执行静态代码质量检查。

### Format Check

确认代码格式符合项目约定。

### Full Test

在 Change 完成或高风险修改后执行必要的完整测试集合。

### OpenSpec Validation

涉及 OpenSpec artifacts 时，执行当前 OpenSpec 版本支持的规范验证命令。

## 执行顺序

单个原子 Task 默认采用：

1. 当前 Task 的目标测试；
2. 必要的类型检查；
3. 必要的 lint / format 检查；
4. 相关回归测试。

Change 接近完成时再根据风险执行更大范围验证。

优先快速失败，避免每次微小修改都运行高成本全量检查。

## 命令失败

命令失败时：

- 保留实际错误输出；
- 判断失败是否由当前修改造成；
- 不得通过跳过检查或降低规则制造假通过；
- 同一问题反复失败时遵循 Apply / Testing 的三次失败原则。

## 禁止虚构命令

如果项目尚未提供某项标准命令：

- 明确说明当前不存在统一入口；
- 使用底层工具的真实命令完成必要验证；
- 不得为了符合规则而虚构 `make`、npm script 或其他命令。

是否需要新增统一工程命令，应作为正常的 OpenSpec Change 决策，而不是在当前任务中顺手添加。

## 提交

提交应保持原子性，一个提交对应一个逻辑完整且已验证的 Task。

提交信息遵循 Conventional Commits 风格：

`<type>(<scope>): <description>`

如果当前项目已经确定 OpenSpec Change / Task 标识格式，则按项目约定附加。

不得在尚未确定统一格式时自行发明新的提交元数据协议。
