# 权限与授权规则

## 适用范围

当当前 Change 涉及以下任一方面时，必须读取并遵循本规则：

- 身份认证；
- 主体识别或主体传递；
- 授权或访问控制；
- 角色、权限、成员关系、所有权或共享关系；
- 对受保护资源的读取、创建、修改、删除或执行；
- 跨用户、组织、租户、项目、工作区或其他资源边界的访问；
- API Key、服务主体、自动化任务或代理执行；
- 任何涉及“谁可以在什么条件下对什么资源执行什么操作”的行为。

## 核心授权模型

每个受保护操作都必须能够明确回答：

- `principal`：谁发起操作；
- `action`：执行什么操作；
- `resource`：操作什么资源；
- `context`：做出授权判断需要哪些上下文；
- `identity source`：主体身份从哪里产生；
- `decision point`：授权决定在哪里做出；
- `enforcement point`：允许或拒绝最终在哪里执行。

不得只使用“管理员”“普通用户”“内部接口”等模糊描述替代真实授权模型。

## 基本原则

权限需求由当前项目的业务规则和 Specs 决定。

不得仅根据：

- 角色名称；
- 路由名称；
- UI 是否显示；
- 资源 ID 是否难猜；
- 某个上游已经认证；
- 历史项目经验；

推断某个操作已经安全。

认证只证明主体身份，不自动代表主体拥有目标资源的访问权限。

关键授权信息无法确认时，应默认拒绝，而不是默认放行。

## 授权执行边界

授权必须在可信执行边界完成。

可信边界可能位于：

- 当前应用；
- API 层；
- 业务服务；
- 独立授权服务；
- API Gateway；
- 外部身份或策略系统；
- 其他实际负责授权的组件。

不得在本通用规则中预设授权一定由哪一层负责。

Design 必须根据当前架构明确：

- 授权决定由谁负责；
- 最终拒绝能力位于哪里；
- 是否存在多个授权层；
- 各层分别负责什么。

## 主体真实性

验证权限行为时，应使用与真实业务路径一致的主体类型和身份上下文。

不得使用：

- 管理员；
- 超级用户；
- 高权限服务主体；
- 特权测试凭据；

替代普通业务主体路径，以此掩盖实际授权差异。

如果不同主体类型存在不同授权路径，例如：

- 真人用户；
- API Key；
- 服务主体；
- 自动化任务；
- Agent 或 Tool；

必须分别明确：

- 主体如何确定；
- 身份如何传播；
- 使用什么授权上下文；
- 是否改变原有访问边界。

## 资源级授权

仅完成认证不代表拥有目标资源的访问权限。

涉及具体资源时，应验证：

- 资源归属；
- 主体与资源的关系；
- 所有权；
- 成员关系；
- 共享关系；
- 组织或租户边界；
- 项目或工作区边界；
- 状态约束；
- 其他会影响授权结果的上下文。

必须考虑横向访问风险，即：

一个合法主体是否能够访问不属于其授权范围的其他资源。

单条、批量、管理、共享或其他不同入口不得互相推断安全性。

每个实际入口都应根据其真实调用链判断。

## 身份与授权上下文传播

当请求跨越：

- 模块；
- Service；
- Process；
- Queue；
- Job；
- Tool；
- Agent；
- 外部 API；
- 其他系统边界；

必须确认必要的身份和授权上下文是否：

- 正确传递；
- 没有丢失；
- 没有被替换成更高权限主体；
- 没有被无意扩大；
- 没有跨越不允许的资源边界。

不得仅因为入口已经完成授权，就假设下游所有操作天然安全。

## 外部依赖

如果身份、授权判断、策略、资源范围或主体信息依赖项目边界之外的组件，应读取并遵循：

`docs/rules/external-dependency.md`

然后通过：

`docs/context/index.yaml`

发现当前项目是否登记了与该依赖相关的 Context。

不得预设：

- 外部组件一定执行授权；
- 外部组件一定不执行授权；
- 当前项目一定需要补充授权；
- 授权责任一定由双方共同承担。

必须根据实际架构和真实行为查证：

- 谁提供主体身份；
- 谁提供授权判断所需的资源与关系信息；
- 谁作出授权决定；
- 谁执行最终允许或拒绝；
- 哪些身份与授权上下文需要跨边界传播；
- 外部依赖的相关能力、限制和契约是否已有可验证证据。

## 权限契约

涉及新增或修改受保护操作时，Specs / Design 应能够明确回答：

- `principal` 是谁；
- `action` 是什么；
- `resource` 是什么；
- 授权判断需要哪些 `context`；
- `identity source` 在哪里；
- `decision point` 在哪里；
- `enforcement point` 在哪里；
- 跨系统或跨模块时，各边界分别承担什么责任；
- 什么条件允许；
- 什么条件必须拒绝。

不得只写“需要 RBAC”“检查权限”“需要鉴权”或类似无法确定性验证的描述。

## 验证要求

重要权限行为必须同时考虑正向和反向验证。

应根据当前 Requirement 和真实风险验证：

- 合法主体在满足条件时能够执行；
- 未认证主体被拒绝；
- 权限不足主体被拒绝；
- 无权访问其他主体资源；
- 跨组织、租户、项目、工作区或其他隔离边界的访问被拒绝；
- 所有权、成员关系、共享关系或资源状态变化后的行为；
- 不同入口是否保持一致的授权约束；
- 不同主体类型是否经过正确的授权路径；
- 身份与授权上下文在调用链中是否正确传播；
- 授权上下文丢失、替换或被扩大时是否能够被安全拒绝。

不得仅因为管理员、超级用户或高权限服务主体路径测试通过，就认为普通业务主体的权限实现正确。

## Evidence 与可复用结论

对项目边界之外的依赖进行实际核验后，如果某项事实：

- 已经有可靠证据；
- 预计会被后续多个 Change 复用；
- 属于项目长期有效的上下文，而不是当前 Change 的临时调查结果；

可以将其整理为项目专属 Context，并在：

`docs/context/index.yaml`

中显式登记。

可复用事实应根据实际情况区分：

- 源码或实现事实；
- API / Schema / Protocol 契约；
- 配置事实；
- 版本或部署事实；
- 运行态验证；
- 尚未核验内容。

不得把假设、计划、推断或模板字段记录成已经验证的事实。

本通用规则不预设固定 Evidence 文件名，也不要求项目一定存在外部依赖 Evidence。

## 最小范围原则

权限查证应按当前 Change 的实际影响范围增量执行。

不要求为了一个局部权限需求：

- 审计整个项目；
- 审计整个外部依赖；
- 预先建立完整授权基础设施；
- 加载所有可能相关的项目上下文。

但不得因为已有历史记录或项目 Context，就跳过当前 Change 必要的：

- 主体来源确认；
- 授权责任判断；
- 资源范围判断；
- 身份与授权上下文传播确认；
- 正向与反向验证。

最终判断应以当前可验证的项目事实、契约和运行行为为准。
