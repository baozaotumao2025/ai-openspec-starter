# Design 阶段规则

## 阶段目标

Design 负责说明如何满足已经确认的 Specs，并明确模块边界、依赖关系、数据流和关键技术决策。

设计应保持简单，优先复用现有架构，不为尚未出现的需求提前建设扩展点。

## 基本设计原则

- 遵循 KISS、YAGNI、DRY、SOLID。
- 优先采用项目已有模式，除非现有模式无法满足 Specs。
- 不得为了“未来可能需要”增加抽象层、配置项或扩展机制。
- 存在明显技术债、架构冲突或可复用现有能力时，必须在 Design 中明确指出。

## 纵向切片与领域边界

业务能力优先按领域纵向切片组织。

每个领域应尽量满足：

- 自包含；
- 单一业务关注点；
- 明确的公共边界；
- 可独立测试；
- 内部实现不被其他领域直接依赖。

OpenSpec capability 与代码领域应尽量保持清晰映射，避免一个 capability 横跨大量无关模块。

## 跨领域通信

跨领域协作优先通过：

- 明确的公共契约；
- 领域事件；
- Port / Protocol / Interface；
- 强类型 DTO。

不得让一个领域直接依赖另一个领域的内部 Service 或内部实现细节。

## Ports and Adapters

核心业务逻辑依赖抽象能力，而不是具体基础设施实现。

当存在真实的外部依赖、多实现需求或测试隔离需求时：

- 在业务侧定义 Port；
- Adapter 实现 Port；
- 通过依赖注入完成装配。

不得为了单一简单调用点人为创建无意义接口或工厂。

## 持久化边界

涉及数据库时：

- 每个领域维护自己的持久化写入责任；
- 禁止跨领域直接修改其他领域的数据；
- 跨领域引用优先使用标量 ID 和明确契约；
- 避免 ORM 导航关系把不同领域隐式耦合在一起；
- 跨领域读取需要明确的数据契约，而不是传播其他领域的 ORM 实体。

## 数据与状态

跨边界 DTO 和领域事件优先设计为不可变对象。

涉及复杂状态流转时：

- 明确合法状态集合；
- 明确允许的状态跃迁；
- 非法跃迁必须有显式失败行为；
- 避免通过任意字段赋值绕过状态约束。

## 可测试性设计

涉及时间、随机数、UUID、外部网络、存储或其他不确定性依赖时，应评估是否需要通过显式依赖或 Port 隔离，以支持确定性测试。

具体测试执行策略由 Apply/Testing 规则负责。

## Design 输出要求

Design 应明确：

1. 模块与领域边界；
2. 数据流和主要依赖方向；
3. 项目边界之外的依赖及接口边界；
4. 关键技术决策及原因；
5. 与现有架构不同的地方；
6. 风险、迁移或兼容性影响；
7. Specs 如何映射到设计。


不得在 Design 中展开成逐文件实施清单；具体实施步骤进入 `tasks.md`。

## 数据库设计

如果当前 Change 涉及数据库、持久化、ORM、Schema 或 Migration，
必须读取并遵循 `docs/rules/database.md`。

## OpenSpec 与代码领域映射

OpenSpec capability / domain 与代码中的业务领域应保持清晰、可追溯的语义映射。

但不要求：

`openspec/specs/<domain>/`

与某个具体源码目录机械保持物理 1:1。

实际代码结构应根据：

- 业务边界；
- 模块职责；
- 当前技术栈；
- 仓库已有组织方式；

确定。

Design 必须能够说明某个 Spec capability 由哪些代码模块负责实现。

如果一个 capability 横跨大量无关模块，或一个模块同时承担多个无关领域，应视为边界设计风险并重新评估。

不得仅为了目录形式一致而搬迁代码或制造无意义模块。


## 权限设计

如果当前 Change 涉及以下任一方面：

- 身份认证或主体传递；
- 授权或访问控制；
- 角色、权限、成员关系、所有权或共享关系；
- 对受保护资源的读取、创建、修改、删除或执行；
- 跨用户、组织、租户、项目、工作区或其他资源边界的访问；
- API Key、服务主体、自动化任务或 Agent / Tool 代表其他主体执行操作；

则必须读取并遵循：

`docs/rules/authorization.md`

Design 必须明确：

- principal：谁发起操作；
- action：执行什么操作；
- resource：操作什么资源；
- context：做出授权判断所需的上下文；
- identity source：主体身份从哪里产生；
- decision point：授权决定在哪里做出；
- enforcement point：拒绝或允许最终在哪里执行；
- 身份和授权上下文如何跨模块或服务边界传播；
- 关键允许路径；
- 关键拒绝路径；
- 必要的验证策略。

不得预设授权一定由当前项目、某个外部服务或某个固定架构层负责。

授权责任必须根据当前项目的实际架构和当前 Change 的需求确定。

如果身份、授权判断或资源范围依赖项目边界之外的组件，应读取并遵循：

`docs/rules/external-dependency.md`

然后通过：

`docs/context/index.yaml`

发现当前项目是否登记了与该依赖相关的 Context。

如果没有相关 Context，不得自行假设该依赖的授权能力、身份模型、角色模型或资源范围。

需要依赖外部组件的实际行为进行设计时，应先进行针对性查证，再在当前 Design 中明确：

- 哪些事实来自当前项目；
- 哪些事实来自外部依赖；
- 哪些行为由哪一层负责；
- 哪些结论已经验证；
- 哪些仍属于未确认假设。

不得仅根据角色名称、接口名称、历史调查或过去项目经验推断当前授权行为。
