# Proposal 阶段规则

## 阶段目标

Proposal 用于明确为什么要做这次变更、变更边界、影响范围以及需要进一步设计的关键问题。

不在 Proposal 中提前锁死具体实现细节。

## 上下文与领域对齐

- 基于当前 Change 已选择的项目上下文进行分析。
- 如果涉及既有能力，先检查相关 `openspec/specs/`。
- 如果项目存在 `docs/glossary.md`，涉及领域实体、角色、权限、状态和业务动作时必须使用其中定义的术语。
- 不得凭通用语义自行发明已经存在领域概念的替代名称。

## Proposal 必须明确

1. 为什么需要这次变更；
2. 要解决的核心问题；
3. 本次变更包含什么；
4. 明确不包含什么；
5. 影响哪些已有 capability、模块或项目边界之外的依赖；
6. 已知风险、约束和未知项。

## 决策分叉

如果当前变更存在真实的多路径技术或架构选择：

- 明确列出关键决策点；
- 描述每个方案的主要取舍；
- 标记尚需人类裁决的问题；
- 在尚未作出关键裁决时，不得把某一方案伪装成已经确定的事实。

不得为了满足格式要求而人为制造不存在的架构分叉。

## 边界

- Proposal 描述 WHAT 和 WHY。
- 详细行为要求进入 specs。
- 技术实现方案进入 design。
- 实施步骤进入 tasks。

## 权限敏感变更

如果当前 Change 涉及以下任一方面，应视为权限敏感 Change：

- 身份认证或主体传递；
- 授权或访问控制；
- 角色、权限、成员关系、所有权或共享关系；
- 对受保护资源的读取、创建、修改、删除或执行；
- 跨用户、组织、租户、项目、工作区或其他资源边界的访问；
- API Key、服务主体、自动化任务或 Agent / Tool 代表其他主体执行操作；
- 任何涉及“谁可以在什么条件下对什么资源执行什么操作”的行为。

Proposal 必须明确指出该 Change 是否可能改变现有安全或授权边界。

Proposal 至少说明：

- 哪类主体可能受影响；
- 哪类受保护资源或操作可能受影响；
- 是否可能扩大、缩小或改变已有访问边界；
- 是否存在跨主体或跨资源边界访问风险；
- 身份或授权上下文是否需要跨模块、服务或系统边界传播；
- 是否存在尚未确认的权限问题，需要在 Specs / Design 阶段进一步定义。

如果权限行为依赖项目边界之外的组件，只需在 Proposal 中指出这一依赖和待确认事项。

不得在 Proposal 阶段假设该外部组件具有什么能力，也不得提前决定授权责任由哪一层承担。

后续需要查证外部依赖真实行为时，应按照：

`docs/rules/external-dependency.md`

并结合当前项目在：

`docs/context/index.yaml`

中实际登记的 Context 进行调查。

Proposal 阶段不定义最终角色矩阵、具体授权执行点或实现方案。

如果某项权限边界仍未知，应明确记录为风险或待确认事项，并留到 Specs / Design 阶段定义和验证。
