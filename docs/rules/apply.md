# Apply 阶段规则

## 阶段目标

Apply 负责按照已经确认的 OpenSpec Change 实施代码变更。

实现必须以当前 Change 的：

- proposal；
- specs；
- design；
- tasks；

为约束，不得在编码过程中擅自重新定义需求或架构。

## 开始实施前

开始具体任务前：

1. 读取当前 Change 的 artifacts；
2. 确认当前正在执行的 task；
3. 读取该任务涉及的必要项目上下文；
4. 检查任务依赖是否已经完成；
5. 确认不存在尚未解决的关键决策。

不得因为已经理解整个 Change，就一次性加载所有源码和项目背景。

## 按任务实施

严格按照 `tasks.md` 的依赖顺序实施。

每次优先完成一个原子任务：

- 修改必要代码；
- 执行该任务定义的验证；
- 确认验证通过；
- 更新任务状态；
- 再进入下一任务。

不得把多个无关任务合并为一次大规模修改。

## 精确修改

只修改完成当前 Requirement / Task 所必需的内容。

禁止：

- 顺手重构无关模块；
- 顺手统一无关代码风格；
- 删除与当前 Change 无关的旧代码；
- 添加当前需求没有要求的扩展能力；
- 为假设中的未来需求提前增加抽象或配置。

每一处重要 Diff 都应该能够追溯到当前 Change。

## 上下文控制

分析现有代码时：

- 优先读取目标文件及直接依赖；
- 必要时使用当前项目可用的结构化导航能力（如 CodeGraph、LSP、AST、调用关系、引用关系或仓库搜索）扩展上下文；
- 不默认读取整个模块或整个仓库；
- 涉及接口、共享状态或公共契约时，必须分析下游影响后再修改。

## 设计漂移

如果实现过程中发现 Specs 或 Design 无法正确落地：

不得直接在代码中绕过。

应：

1. 停止当前实现；
2. 明确指出发现的设计缺口；
3. 回到对应 OpenSpec artifact 修正；
4. 在重新确认后继续 Apply。

代码不得成为未记录设计决策的唯一事实来源。

## 失败处理

同一问题连续尝试三次仍无法通过验证时：

- 停止继续猜测式修改；
- 总结已经尝试的方法；
- 保留关键错误信息；
- 重新检查假设、上下文和设计；
- 必要时将问题升级为阻塞项。

不得通过删除测试、放宽断言或绕过错误来制造“通过”。

## 提交原则

完成一个逻辑完整且验证通过的原子任务后，优先形成原子提交。

提交不得混入与当前任务无关的修改。

具体提交格式遵循项目 Git 规则。

## Apply 完成条件

只有满足以下条件，才能认为 Apply 完成：

1. `tasks.md` 中计划实施的任务已经完成；
2. 每个任务的验证信号均已执行；
3. Specs 与实现不存在已知漂移；
4. 没有通过临时绕过方式隐藏失败；
5. 剩余问题已经明确记录。

## 实施规则加载

进入具体 Task 后，根据实际修改内容按需加载专项规则。

### 业务代码修改

如果当前 Task 涉及新增或修改业务代码：

- 读取并遵循 `docs/rules/code-quality.md`。

### 行为实现与测试

如果当前 Task 涉及新增、修改或修复系统行为：

- 读取并遵循 `docs/rules/testing.md`。
- 默认采用 RED → GREEN → REFACTOR → VERIFY。

纯文档、纯配置或不涉及可执行行为的变更，不要求机械执行 TDD。

### 数据库实现

如果当前 Task 涉及数据库、ORM、Repository、Schema 或 Migration：

- 读取并遵循 `docs/rules/database.md`；
- 以当前 Change 已确认的 Design 为实现依据；
- 不得在 Apply 阶段自行改变领域数据边界或跨领域关系设计。

### 最小上下文原则

只加载当前 Task 实际需要的专项规则。

不得因为进入 Apply 就一次性加载所有 `docs/rules/` 文件。

### 会话连续性

如果当前 Change 出现以下情况之一：

- 工作需要跨会话继续；
- 当前工作需要中断；
- 出现阻塞项；
- 剩余工作仍较多且当前上下文不足以安全继续；

则读取并遵循 `docs/rules/session-continuity.md`，并按要求创建或更新：

`openspec/changes/<change-id>/handoff.md`

正常短任务无需创建 handoff。

## Apply 执行模式

### 默认模式：连续推进

如果用户没有要求逐步确认：

- 按 `tasks.md` 的依赖顺序持续执行；
- 每个原子 Task 都必须完成实现、验证和状态更新；
- 一个 Task 完成后可以继续下一个；
- 遇到阻塞、关键未决策、验证失败或需要修改 Specs / Design 时立即停止。

默认模式不代表可以跳过 Task 级验证，也不代表可以把多个 Task 合并成一次大修改。

### 单步模式：Stop-and-Wait

如果用户明确要求：

- 单步执行；
- step-by-step；
- 每一步确认；
- 做完一步再继续；
- 或其他等价表达；

则进入单步模式。

单步模式下：

1. 每次只执行一个未完成的原子 Task；
2. 完成该 Task 的实现；
3. 执行该 Task 的验证；
4. 更新 `tasks.md` 状态；
5. 如适合提交，则完成原子提交；
6. 向用户汇报本步改动、验证结果和剩余状态；
7. 停止，不得擅自进入下一个 Task。

除非用户明确解除单步模式，否则后续 Apply 继续保持 Stop-and-Wait。

### 工程验证

如果当前 Task 涉及：

- 业务代码；
- 可执行代码；
- 依赖或构建配置；
- 类型、Lint、格式化或测试验证；

则读取并遵循 `docs/rules/engineering-workflow.md`。

执行验证前必须先确认项目真实存在的工具链和命令，不得凭旧规则或经验虚构 `make`、npm script 或其他命令。

纯文档类 Task 不要求加载该规则。

### 跨模块上下文边界

涉及跨模块依赖时，默认采用 Spine / 1-Hop 上下文策略。

优先读取：

- 公共接口；
- Port / Protocol / Interface；
- 函数或方法签名；
- 直接关联的输入 DTO；
- 直接关联的输出 DTO；
- 必要的公开类型与错误契约。

在这些信息足以完成当前 Task 时，不继续展开外部模块内部实现。

只有出现以下情况之一时，才继续读取外部实现：

- 公共契约不足以判断真实行为；
- 实现与声明存在疑似不一致；
- 当前问题发生在 Adapter 或集成边界；
- 需要确认副作用、事务或错误传播；
- 当前可用的结构化导航、引用关系或调用链分析表明问题实际位于下游实现。

继续下钻时只读取解决当前问题所需的最小范围，不默认展开整个模块。

涉及状态流转时，应优先定位状态定义、合法跃迁规则和直接读写引用，再决定是否扩大上下文。

### 权限实现

如果当前 Task 涉及以下任一方面：

- 身份认证或主体传递；
- 授权或访问控制；
- 角色、权限、成员关系、所有权或共享关系；
- 对受保护资源的访问或操作；
- 跨用户、组织、租户、项目、工作区或其他资源边界的访问；
- API Key、服务主体、自动化任务或代理执行；

则必须读取并遵循：

`docs/rules/authorization.md`

实施时必须以当前 Change 已确认的 Specs 和 Design 为依据。

不得在 Apply 阶段自行改变：

- principal；
- action；
- resource；
- 授权边界；
- decision point；
- enforcement point；
- 身份或授权上下文传播方式。

如果实现依赖项目边界之外的组件，应读取并遵循：

`docs/rules/external-dependency.md`

并通过：

`docs/context/index.yaml`

加载当前项目实际登记、且与当前 Task 相关的 Context。

不得假设外部依赖已经具备某项授权、身份或资源隔离能力。

需要调查外部依赖或调用链时，应使用当前环境实际可用的导航工具。

如果 CodeGraph 已安装并完成相关仓库索引，可以优先使用；否则使用 LSP、IDE 引用搜索、`rg`、仓库搜索、正式契约或直接源码分析。

最终实现判断必须以实际源码、正式契约、配置或已经确认的运行行为为依据。

不得通过管理员凭据、超级用户身份或高权限服务主体绕过正常业务授权路径来使实现或测试通过。
