# 外部依赖查证规则

## Purpose

本规则定义当前项目依赖项目边界之外的组件时，如何进行事实查证、风险控制和证据管理。

外部依赖可能包括但不限于：

- 第三方 API 或 SaaS；
- 独立部署的内部服务；
- 外部数据库、消息系统或基础设施；
- 外部代码仓库或参考源码；
- 第三方 SDK、Library 或 Framework；
- 身份提供者、支付系统、对象存储等外部能力。

项目不一定存在外部依赖。

不得因为本规则存在，就假设当前项目必须存在或集成某个外部依赖。

## Context Discovery

当当前 Change 依赖某个外部组件时：

1. 先读取 `docs/context/index.yaml`；
2. 查找当前项目是否已经登记与该依赖相关的 Context；
3. 只读取当前 Change 实际需要的相关 Context；
4. 如果没有登记相关 Context，不得自行假设该外部依赖的版本、位置、配置或行为。

不得因为涉及外部依赖，就默认加载所有外部依赖资料。

## Default Boundary

除非当前 Change、项目规则或用户明确授权，否则默认：

- 不修改外部仓库源码；
- 不修改外部依赖的数据；
- 不启动、停止或重新配置外部服务；
- 不改变外部依赖的权限或基础设施；
- 可以读取允许访问的文档、源码、配置和正式接口契约；
- 只调查解决当前 Change 所需的最小范围。

具体外部依赖的：

- 地址；
- 仓库；
- 版本；
- API；
- 凭据使用方式；
- 运行环境；
- 可执行操作边界；

属于具体项目 Context，不属于本通用规则。

## Investigation Principle

当 Change 的设计、实现或验证依赖外部组件的真实行为时，不得仅依据：

- 组件名称；
- API 名称；
- 类型名称；
- 历史文档；
- 旧项目经验；
- 模型已有知识；
- 历史调查结果；
- 测试替身行为；

直接推断当前事实。

应针对当前问题进行最小范围的实际查证。

## Evidence Priority

事实证据优先级通常为：

1. 当前实际源码或正式机器可读契约；
2. 当前实际配置；
3. 当前环境的确定性运行验证；
4. 当前版本官方文档；
5. 项目中已经记录且仍适用的历史 Evidence；
6. 历史记录、经验或推测。

不同类型事实应采用最适合其性质的证据来源。

不得用低优先级证据覆盖已经确认的高优先级事实。

## Source Fact and Runtime Fact

必须区分静态事实与运行事实。

### Source Fact

描述源码、协议或正式契约明确规定了什么。

例如：

- API 是否存在；
- 参数和返回值如何定义；
- 授权判断在哪里执行；
- 某个字段如何持久化；
- 错误如何传播。

### Runtime Fact

描述当前实际环境启用了什么或正在运行什么。

例如：

- 某项能力是否通过配置开启；
- 当前部署版本；
- 当前连接的服务；
- 某个插件是否启用；
- 当前环境实际暴露的能力。

源码存在某项能力，不代表当前环境一定启用。

当前环境表现出的行为，也不能自动推断为稳定的源码或 API 契约。

## Tooling

用于源码和调用链调查时，应优先使用当前项目已经可用的结构化导航工具。

如果 CodeGraph 已安装并完成当前仓库索引，可以优先用于：

- 符号定位；
- 引用关系；
- 调用链；
- 依赖关系；
- 状态读写关系。

如果 CodeGraph 不可用、未初始化或无法覆盖目标内容，则使用当前环境实际可用的替代方式，例如：

- LSP；
- IDE symbol/reference search；
- `rg` / `grep`；
- 仓库搜索；
- 直接读取源码；
- 官方 API / Schema / Contract。

工具只用于定位和缩小调查范围。

最终事实判断仍应以实际源码、正式契约、配置或确定性运行验证为准。

## Scope of Investigation

只调查与当前 Change 直接相关的：

- API；
- 服务；
- 数据模型；
- 权限边界；
- 调用链；
- 配置；
- 持久化行为；
- 错误传播；
- 外部能力复用点。

避免因为一个局部问题审计整个外部依赖。

如果已有公共契约足以回答当前问题，不继续无目的地下钻内部实现。

## Authorization Dependency

如果当前项目的授权行为依赖外部组件，不得预设授权责任属于某个固定系统。

应根据实际架构查证：

- 谁提供身份；
- 谁执行授权判断；
- 谁控制资源范围；
- 哪一层可以最终拒绝请求；
- 身份和授权上下文如何跨边界传播。

最终责任模型应记录在当前 Change 的 Specs / Design 或项目对应 Context 中，而不是固化在本通用规则中。

## Historical Evidence

历史 Evidence 只能作为调查入口，不能自动视为当前事实。

复用历史结论前，应确认它仍覆盖当前问题所涉及的：

- 操作；
- 主体或身份；
- 资源范围；
- 源码、API 或依赖版本；
- 配置；
- 部署方式。

如果关键条件已经变化或未知，应进行新的针对性查证。

## Evidence Lifecycle

当前 Change 中产生的调查结果，默认保存在当前 Change 中。

只有当某项事实：

- 已经过实际查证；
- 适用范围明确；
- 版本或配置范围明确；
- 后续多个 Change 很可能复用；
- 不包含仅属于当前 Change 的设计决定；
- 明确知道什么情况下需要重新验证；

才适合提升为长期项目 Context。

长期 Evidence 应写入当前项目已经在 `docs/context/index.yaml` 中登记的合适位置。

如果当前项目尚未定义长期 Evidence 存储位置：

- 不自动创建固定名称的 Evidence 文件；
- 不因为本次调查强制建立新的 Context；
- 可以先将结果保留在当前 Change 中；
- 需要长期保存时，再为该具体项目设计并登记对应 Context。

不得建立多个相互独立、可能漂移的长期事实源。
